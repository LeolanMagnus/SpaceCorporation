## 0. В15 — разрешаемое противоречие (читать ПЕРЕД кодом)

**Конфликт.** `prototype-plan.md` Этап 3 описывает выстрел как RPC с клиентской
точкой прицела и синхронизацию мишеней через `MultiplayerSynchronizer`, но в
реализованной стадии 2 есть три места, где этот текст расходится с кодом:

| | `prototype-plan.md` Этап 3 | реальность стадии 2 |
|---|---|---|
| Транспорт выстрела | `rpc_id(1, "RequestFire", aimPoint, tick)` — один RPC | `RpcSubmitInput` (`Ship.cs:946-947`) идёт `Reliable, Channel 1`, хотя план стадии 2 предписывал вводу `Unreliable, Channel 2` (`stage2-plan.md:151-152`, §1.3; rework §2.3 строка 390 и §2.9 строка 753); канал 2 (`ChannelCount = 3`, `NetworkManager.cs:53`) объявлен и **не используется** |
| Откуда берётся прицел | клиент шлёт `aimPoint` (мировую точку) | у клиента нет права на мировую геометрию: `Ship` — авторитет сервера (`Freeze = (auth != 1)`), пилот рисует hull по **своему предсказанию**, и расхождение с сервером nonzero при лаге (порог `ReconcileThreshold = 0.3`, `Ship.cs:178`) |
| Свойство HP | `TargetHealth` через `MultiplayerSynchronizer` | конфиг репликации — `.tres` с путями **через двоеточие** (`NetState:NetPosition`), иначе ресурс пустой (замечено в `scenes/ShipReplication.tres`); `replication_interval` в Godot 4.7 для `OnChange` не работает → частоту задаёт гейт публикации на сервере |

**Почему это нельзя оставить как есть.** Буквальное «клиент прислал `aimPoint` —
сервер в него и попал» означает, что клиент, у которого корабль на 0.3 м впереди
серверного (реконсиляция ещё не пришла), стреляет из позиции, которой на сервере
нет. Критерий готовности Этапа 3 («если клиент „схитрил" и прислал ложный
`aimPoint` — сервер всё равно считает по своей симуляции») тогда выполняется
формально и проваливается по существу: сервер считает по **чужой** геометрии.

**Решение В15 (принято в этой стадии): клиент шлёт намерение, сервер считает сам.**

1. Выстрел — событие, а не кадр: `RpcRequestFire(shipNetId, tick, aimPoint)` по
   образцу `RpcSubmitInput` (`AnyPeer`, `CallLocal = false`), но **`Reliable`,
   канал 1** — потерянный выстрел это потерянный выстрел, а не потерянный кадр
   ввода; надёжность здесь дешевле и не ломает реконсиляцию, потому что выстрел
   не участвует в интегрировании.
2. `aimPoint` (мировая точка) **не является истиной**: сервер сам строит луч —
   из **своего** `Muzzle.GlobalPosition` (позиция корабля серверная, это и есть
   «считает по своей симуляции») и по **своему** направлению прицела: сервер
   уже интегрирует `LookYaw`/`LookPitch` из `InputFrame` пилота, значит его
   `Basis` содержит те же довороты мыши, что и предсказание пилота. Присланный
   `aimPoint` — только подсказка: сервер сверяет с ней свой луч по углу
   (допуск `AimToleranceM`, В17 п.3) и стреляет **по своему** лучу, а не по
   чужой точке. Расхождение предсказания пилота (`predErr < 0,3 м`) при
   дистанции прицела 10+ м даёт доли градуса — в допуск укладывается.
3. Визуал луча клиент рисует **до** подтверждения (0.2 с, белая полоса) — ровно
   как требует `prototype-plan`; это предсказание картинки, а не попадания.
4. Мишени — спавн сервером через `MultiplayerSpawner` (`WorldSpawner` уже
   регистрирует спавнабельные сцены, `WorldSpawner.cs:69-70`) + отдельный
   `TargetReplication.tres` с путями через двоеточие.
5. Реестр мишеней — по образцу реестра кораблей (`RegisterShip` /
   `FindShip(shipNetId)`, `NetworkManager.cs:168-190`): сервер обязан уметь
   превратить `targetId` из RPC в узел, и обязан не находить чужой/несуществующий
   id.

**Что это ломает и как чинится (обязательный список, а не «потом»):**

| ломается | где | как чинится в этой стадии |
|---|---|---|
| ЛКМ нигде не назначена | `project.godot [input]` | добавить действие `fire` (MouseButton Left); ловит его `ShipMouseCatcher` (у `RigidBody3D` свой `_input` вьюпорт зовёт только при пикинге — вывод стадии 2, `stage2-plan` шаг 2.2, отклонение 1) |
| ЛКМ в `Interaction`-режиме кликает по UI | `Ship.IsInteractionMode` | гейт: выстрел только в `Pilot`-режиме и только при `AimOnShip` (тот же гейт, что у мыши доворота, `AimRadiusM = 6`) |
| Маска луча | `CollisionLayers.LaserMask` уже объявлена (`Station \| Target`) и не используется | использовать её в `IntersectRay`; `Target = 8` уже в перечне слоёв |
| `Clear Targets` должен удалять узлы у всех | `MultiplayerSpawner` | удаление **только сервером** (`QueueFree` на сервере → спавнер сам удаляет у пира); вручную RPC-удаление не слать |
| Поздно зашедший пир не увидит мишени | `TargetReplication.tres` | `spawn = true` для HP/позиции — по образцу `ShipReplication.tres` |

## 1. Что именно строим (термины, а не «реализуем стрельбу»)

- **3.1 `Target.tscn`** — мишень: `RigidBody3D` (выбор против `StaticBody3D` — В16 в §0) с
  `collision_layer = Target (8)`, `collision_mask = 0`, `MeshInstance3D`,
  `Node3D:TargetState` c `[Export]`-свойствами (`TargetNetId`, `Hp`, `MaxHp`,
  `HitPoint`, `HitTick`) + `MultiplayerSynchronizer` с `TargetReplication.tres`.
  Хелсбар — `Node3D`-билборд (`SubViewport`/`Sprite3D` НЕ нужен: достаточно
  `MeshInstance3D`-полоски, масштаб которой берётся из реплицированного `Hp`).
- **3.2 Реестр мишеней** в `NetworkManager`: `RegisterTarget` / `UnregisterTarget` /
  `FindTarget(int targetNetId)` — копия реестра кораблей (`NetworkManager.cs:168-189`).
  Адрес выдаётся **до** `AddChild` (то же правило, что и для кораблей:
  `WorldSpawner.SpawnShipFromScene`, иначе RPC теряются).
- **3.3 Выстрел**: `Ship.RpcRequestFire(shipNetId, tick, aimPoint)` →
  серверный `FireHitscan(ship, frame)` → `RpcOnHitConfirmed(targetNetId, damage,
  hitPoint, shooterNetId, tick)` всем пирам. Клиентский визуал — `BeamVisual`
  (белая полоса 0.2 с) рисуется в момент клика, до подтверждения.
- **3.4 Урон**: `TargetState.Hp` меняет **только сервер**; `Hp <= 0` → сервер
  `QueueFree()` (спавнер удалит узел у всех) + лог.
- **3.5 Дебаг-панель**: кнопки `Spawn Target` (видна/работает только при `IsServer`,
  `NetworkManager.cs:76`) и `Clear Targets`; источник строки `Fire: shots/hits/rejected`
  через `DebugInfoBus.RegisterInfoSource` (`DebugInfoBus.cs:106`).
- **3.6 Долг стадии 2, закрываемый здесь же**: `RpcSubmitInput` перевести на
  `Unreliable, Channel 2` (канал 2 объявлен и пуст, `ChannelCount = 3`).

**В16 — мишень: `RigidBody3D` или `StaticBody3D`?** Берём `RigidBody3D` с
`FreezeMode = Static` **на всех пирах**: мишень на этой стадии нигде не
симулируется, её координаты задаёт только сервер при спавне. Берём `RigidBody3D`,
а не `StaticBody3D`, по одной причине: Этап 4 потребует урон от столкновений, и
события контактов (`BodyEntered3D`) на `RigidBody3D` приходят симметрично с обеих
сторон, тогда как `StaticBody3D` их только принимает. Цена решения — одна строка
`freeze_mode = 1` в сцене.
Проверка: луч (`IntersectRay` с `LaserMask`) находит мишень на сервере, и
`collision_layer = 8` не даёт ей сталкиваться с кораблём (`ShipMask = Station | Target`
— сталкивается намеренно, это задел под Этап 4; на этой стадии мишень заморожена,
поэтому толчка нет).

**В17 — что именно валидирует сервер.** Не «попал ли клиент», а три вещи:
(1) стреляющий действительно пилот корабля (тот же гейт, что у ввода:
`senderPeer != PilotPeerId`, `Ship.cs:983`); (2) выстрел не чаще
`FireCooldownSec` (иначе спам RPC = флуд); (3) присланный `aimPoint` согласован
с **серверным** лучом по углу в допуске `AimToleranceM` (по умолчанию 0.15 рад ≈
8.6°). Пункт (3) — единственное, что делает фразу «сервер считает по своей
симуляции» проверяемой: без неё клиент может прислать любую мировую точку и
сервер построит к ней луч. С проверкой же сервер стреляет **по своему** лучу
(`-Basis.Z` от серверного `Muzzle`), а чужая точка годится лишь на подтверждение
намерения. Проверка — автотесты п.19 (чужой пир → отклонён) и п.20 (ложный
`aimPoint` → отклонён).

## 3. Чего в этой стадии НЕ делаем

- Headless-экспорт сервера — `prototype-plan.md` относит его к Этапу 7
  (строки 140–143); в `DEVELOPMENT.md:233` он ошибочно записан в «осталось на
  стадию 3». В шаге 3.0 расхождение устраняется в документации, код — не здесь.
- Урон от столкновений и `ShipHealth` — Этап 4. Мишень в этой стадии заморожена,
  контакт с кораблём не считается.
- Разброс/очерёдность/перезарядка/боезапас — нет: один выстрел = один урон.
- Эффекты, звук, трассеры, частицы — только белая полоса 0.2 с и вспышка в точке.
- Предсказание **попадания** на клиенте — запрещено В15: предсказывается только
  картинка луча. Клиент не имеет права знать, жива ли мишень.
- Фильтрация видимости (`visibility_filter`) и interest management — не нужно на
  2–3 кораблях; `PublicVisibility = true` сохраняется.
- Оптимизация трафика сверх 3.9 (квантование, delta-encoding) — только если 3.9
  не сходится по замеру.

## 4. Риски и как они проверяются

1. **Пустой `TargetReplication.tres`** (путь без двоеточия) → HP не доезжает,
   «мишень не умирает» при живом серверном `Hp`. Проверка: п.15 + печать
   `replication_config.properties` при старте. Это уже случалось на стадии 1
   (`ShipReplication.tres`, комментарий про `path.get_subname_count() == 0`).
2. **Гонка `TargetNetId` и спавна узла** — RPC придёт раньше адреса, `FindTarget`
   вернёт `null`. Проверка: адрес выдаётся до `AddChild` (правило
   `SpawnShipFromScene`), assert `TargetNetId != 0` сразу после спавна (п.14).
3. **`IntersectRay` в том же физкадре, что и движение тела.** `PhysicsDirectSpaceState3D`
   актуален после шага физики; вызов из `_Input` (клик) видит состояние прошлого
   кадра. Проверка: серверный хитскан выполняется в `_PhysicsProcess`/в очереди
   выстрелов, а не в обработчике RPC; в тесте п.21 мишень стоит, поэтому риск
   виден только в живом прогоне — фиксируется числом «попал/не попал» при
   `LATENCY=100`.
4. **Спам выстрелов** (`fire` с автоповтором клавиши) → флуд reliable-канала.
   Проверка: `FireCooldownSec` + счётчик `RejectedFireCount` в панели;
   `run-net-demo.sh` с зажатой ЛКМ не должен ронять `packets/s` выше порога
   rework §2.7 (< 50 пакетов/с на игрока).
5. **Двойной источник истины по HP** (RPC `damage` + реплика `Hp`). Проверка:
   хелсбар читает только `Hp`; assert в тесте: после `OnHitConfirmed` с
   `damage = 25` локальный `Hp` обязан равняться серверному, а не «минус 25 от
   локального» (иначе при пропущенной реплике HP разъедется).
6. **Регрессия реконсиляции при переводе ввода на unreliable** (3.8). Проверка:
   `NetTest` (109) + `LATENCY=100 ./run-net-demo.sh 2` со сравнением `predErr`
   с таблицей §2.6. Если `predErr` растёт — причина в потерях кадров, лечится
   не возвратом на `Reliable`, а `AppliedTick`-логикой (она уже есть).
7. **Удаление мишени во время полёта чужого RPC** (`FindTarget` → `null`).
   Проверка: п.25 (процесс жив, warning вместо исключения).
