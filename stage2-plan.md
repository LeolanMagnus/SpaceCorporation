## 0. В14 — разрешаемое противоречие (читать ПЕРЕД кодом)

**Конфликт.** `prototype-plan.md` §0 и Этап 2 требуют одну модель, а реализованная
стадия 1 — противоположную:

| | `prototype-plan.md` §0 / Этап 2 | реализованное `В3 = B` (rework §4) |
|---|---|---|
| Авторитет тела `Ship` | всегда `1` (сервер) | пир-пилот; без пилота — `1` |
| Кто интегрирует `RigidBody3D` | сервер, из `InputFrame` | пилот |
| Клиент | шлёт ввод, предсказывает «призрачное» состояние, делает reconciliation (порог 0.05 м) | интегрирует истину, предсказание «не нужно ни при каких обстоятельствах» |
| Позиция «снизу вверх» | никогда (клиент не шлёт позицию) | `RpcReportNetStateToServer` от пилота, `Reliable` |

**Почему это нельзя оставить как есть.** `В3 = B` держит серверное тело замороженным
(`FreezeMode.Static`) всё время, пока у корабля есть пилот. Следствие зафиксировано
самим rework-планом, §2.10 п.14: «все серверные проверки, которым нужна позиция
корабля под пилотом, читают `NetState`, а не `GlobalPosition`». Но стадии 4 и 5
требуют не «прочитать позицию», а **изменить движение**:

- Этап 4: сервер сам считает урон от столкновений — ему нужно тело, которое он
  интегрирует и на которое может подействовать контакт;
- Этап 5: серверная пружина стыковки (`CustomIntegrator`, `prototype-plan` Этап 5)
  физически невозможна на замороженном теле.

То есть `В3 = B` — тупик для следующего этапа, а `prototype-plan` §0 («Сервер никогда
не доверяет клиентским позициям») прямо запрещает канал `RpcReportNetStateToServer`.

**Решение В14 (принято в этой стадии): возвращаемся к `В3 = A`.**

1. Авторитет тела `Ship` — **всегда `1`**, навсегда. `SetMultiplayerAuthority` для
   корабля больше не вызывается никогда.
2. `PilotPeerId` **сохраняется**, но меняет смысл: не «владелец тела», а
   «источник ввода для этого корабля». Метод `AssignShipAuthority` переименовывается
   в `SetPilot` и делает ровно одну вещь — рассылку `PilotPeerId` всем пирам
   (без `SetMultiplayerAuthority`, без перестройки `Freeze`).
3. Пилотский клиент **предсказывает**: гоняет тот же детерминированный интегратор
   локально и рисует `ShipHull` по своему предсказанию; получает серверные снапшоты
   и делает reconciliation (порог `0.05` м, переигровка неподтверждённых вводов).
4. Чужие клиенты и сервер — только snapshot interpolation (`InterpDelay = 0.1`, уже есть).
5. `RpcReportNetStateToServer` и `_lastAcceptedReportTick` — **удаляются**: клиент
   больше никогда не шлёт позицию.

**Что это ломает и как чинится (обязательный список, а не «потом»):**

| ломается | где | как чинится в этой стадии |
|---|---|---|
| assert'ы `PilotPeerId == 2` после `AssignShipAuthority(2,2)` | `tests/NetTest.cs:358-360, 400-408` | остаются валидны: `SetPilot` по-прежнему меняет `PilotPeerId`. Правится только имя метода в тесте |
| assert'ы `Freeze`/`auth` у не-авторитета | `Ship.ApplyAuthority` | правило переворачивается обратно: `Freeze = !IsServer-authority`, то есть `Freeze = (GetMultiplayerAuthority() != 1)` |
| `Stage1Test` п. «инерция сохранилась» (`|v| > 4.5`) | `tests/Stage1Test.cs:405` | offline-режим обязан интегрировать сам (нет сервера) — `authoritySide = (Role == Offline) \|\| IsServer`, как в `Player` |
| `Nudge Ship` | `Ship.NudgeShip` | в сети кнопка шлёт `RpcNudgeRequest` на сервер (или, что проще и честнее, превращается в `InputFrame`-импульс); в offline — локально |
| `ShipHull` у пилота | `Ship._Process` | у пилота hull рисуется по **предсказанию**, у остальных — по интерполяции; `InterpolateHull` не меняем |

## 1. Что именно строим (детерминированное ядро — основа всего этапа)

Смысл этапа не в «отправить ввод», а в том, чтобы **одна и та же функция движения**
считалась на сервере (истина) и на клиенте (предсказание/переигровка). Если код
разный — reconciliation даёт рывок на каждом пакете, и критерий «не резинит»
невыполним в принципе.

### 1.1 `scripts/core/FlightModel.cs` — чистый интегратор (без узлов)

```csharp
public struct FlightState { public Vector3 Position; public Quaternion Rotation;
                           public Vector3 LinearVelocity; public Vector3 AngularVelocity; }
public struct FlightParams { public float Mass, ThrustLinear, ThrustAngular, LinearDamp, AngularDamp; }
public static class FlightModel
{
    public const float FixedDt = 1f / 60f;   // = physics_ticks_per_second (project.godot:48)
    public static void Integrate(ref FlightState s, uint mask, Vector2 look,
                                 FlightParams p, float dt);
}
```

Правила:

- Никаких обращений к узлам, `GlobalPosition`, `Time`, `Engine` — только аргументы.
  Иначе предсказание и сервер разойдутся.
- Силы и торки — **только в локальных осях** (`prototype-plan` Этап 2,
  `DEVELOPMENT.md:140`): базис берём из `s.Rotation`, не из трансформы узла.
- `linear_damp = 0`, `angular_damp = 1.5` (`prototype-plan` строка 48) применяются
  **внутри модели**, экспоненциально: `v *= exp(-LinearDamp*dt)`. Это обязательно:
  при `CustomIntegrator = true` Godot не применяет damping сам (проверяется пробом,
  шаг 2.1), и «забыть демпфирование» = корабль разгоняется до бесконечности.
- `gravity_scale = 0` + глобальная гравитация уже выключена (`project.godot:47`).

### 1.2 `CustomIntegrator = true` и где именно считать шаг (по пробам)

Изначально план обещал `CustomIntegrator` не включать и писать состояние из
`_PhysicsProcess`. **Пробы это опровергли**: пока тело заморожено — не двигается,
но В14 требует, чтобы сервер интегрировал тело, а размороженное тело движок двигает
сам; запись позиции из `_PhysicsProcess` дала бы **двойное интегрирование**.
Пробы (все в `tests/probes/`) дают точную картину:

| Факт | Проба | Результат |
|---|---|---|
| `linear_damp`/`angular_damp` при `custom_integrator = true` движком **не** применяются | `probe_custom_integrator.tscn` | `custom=true`: \|v\| = 10.00000, \|w\| = 6.00000 (не изменились); `custom=false`: 7.25681 и 3.72222 (применились) |
| Гравитация при `custom_integrator = true` **не** применяется | там же | `v.Y = 0` при `gravity_scale = 1` (в проекте `default_gravity = 0`, `project.godot:47`) |
| Движок **сам** интегрирует позицию из `linear_velocity` | `probe_ci_angular.tscn` | за 10 шагов смещение = 1.000000 = `v·dt·шагов` |
| Движок **сам** интегрирует ориентацию из `angular_velocity` | там же | `euler.Y` = 0.500000 = `w·dt·шагов` |
| Интегрирование движка идёт **до** `_IntegrateForces`, а наши записи внутри вызова **финальны** для шага | `probe_ci_finality.tscn` | `pos_at_entry = (100, 0, 0.016667)` — движок уже сдвинул на `v·dt`; `pos_after_step = (100, 0, 0)` — ровно наша запись |
| Тело за шаг двигается скоростью **предыдущего** шага (explicit Euler) | `probe_ci_order.tscn` | смещение за шаг = `v_до·dt`, а не `v_записанная·dt` |
| `dt` внутри `_IntegrateForces` = `1/physics_ticks_per_second` | `probe_custom_integrator.tscn` | `last dt = 0.0166666666666667` |

Отсюда — окончательная конструкция, без двусмысленности:

- `CustomIntegrator = true` ставится только там, где тело интегрируется (сервер /
  offline); у не-авторитетов тело заморожено и интегратор у них не вызывается;
- шаг считается **нами** в `_IntegrateForces` через `PhysicsDirectBodyState3D`,
  из собственного `FlightState` (не из того, что дал движок), и в конце
  записываются **все четыре** величины: позиция, ориентация, `linear_velocity`,
  `angular_velocity`. Пред-интегрирование движка безвредно — оно перетирается
  нашей записью (проба №3);
- демпфирование и гравитацию модель считает **сама** (движок их не считает),
  поэтому `LinearDamp`/`AngularDamp` тела — значения для модели, а не настройки
  движка;
- `FlightModel.Integrate` — чистая функция, её же вызывает клиент для предсказания
  и переигровки, поэтому сервер и клиент сходятся бит-в-бит (тест 2.1.1).

Риск «движок сам двигает тело» из раздела рисков теперь не риск, а учтённое
поведение. Риск №2 (контакты при записи трансформа) остаётся: на стадии 2
контактов нет, на этапах 4–5 переходим на `MoveAndCollide`.

### 1.3 Ввод: `InputFrame`

Битовая маска + ось мыши (`prototype-plan` строка 51). Один кадр = один снимок
состояния, а не событие.

```
бит 0 W (вперёд, +Z локально)   бит 4 Space (вверх, +Y)   бит 7 X (тангаж -)
бит 1 S (назад)                 бит 5 Ctrl  (вниз, -Y)    бит 8 Q (рыскание -)
бит 2 A (влево, -X)             бит 6 Z     (тангаж +)    бит 9 E (рыскание +)
бит 3 D (вправо, +X)
+ Vector2 look — смещение мыши за кадр (yaw, pitch)
+ uint Tick — счётчик физшагов клиента (не серверных!)
```

- Действия в `project.godot [input]` (`ship_forward`, `ship_back`, `ship_left`,
  `ship_right`, `ship_up`, `ship_down`, `ship_pitch_up`, `ship_pitch_down`,
  `ship_yaw_left`, `ship_yaw_right`) — чтобы раскладка была настраиваемой, а не
  захардкоженной в `Input.IsKeyPressed`.
- Отправка: `RpcId(1, nameof(RpcSubmitInput), tick, mask, look)` с
  `TransferMode = Unreliable`, `TransferChannel = 2` (канал ввода, отдельный от
  репликации — `NetworkManager.ChannelCount = 3`, `NetworkManager.cs:41`).
  Отправка каждый физический шаг, **даже при пустой маске**: сервер обязан знать,
  что ввода нет, иначе отпущенная клавиша «залипает» и корабль разгоняется.
- Гейтинг на сервере: принять ввод может только пир, равный `PilotPeerId` этого
  корабля (аналог `Player.IsRequestFromOwner`, `Player.cs:440`). Чужой ввод →
  `GD.PrintErr` и отказ.

### 1.4 Сервер: очередь вводов и применение

Сервер хранит на корабле последний принятый `(tick, mask, look)` и применяет его на
каждом `_PhysicsProcess`. Пропущенные/дублирующиеся тики не переигрываются — при
`unreliable`-канале это нормально: потерянный кадр ввода = один кадр без силы, что
при 60 Гц ввода незаметно (в отличие от потерянного снапшота состояния).

### 1.5 Эталон для пилота: отдельный RPC-снапшот НЕ нужен

Изначально план предполагал отдельный поток `RpcShipSnapshot` (сервер → пилот),
потому что при В3=B пилот был авторитетом, а `MultiplayerSynchronizer`
**не отправляет реплики авторитетному пиру**. При В3=A (В14) пилот авторитетом
не является — сервер (`1`) им является, — и `Synchronizer` сам рассылает `NetState`
всем остальным, включая пилота. Конфиг уже покрывает нужные свойства:
`NetPosition`, `NetRotation`, `NetLinearVelocity`, `NetAngularVelocity`, `SimTick`
(`scenes/ShipReplication.tres`, все `spawn = true`, `replication_mode = 2` = OnChange).

Следовательно, **отдельного `RpcShipSnapshot` в этой стадии нет**: серверный эталон
для реконсиляции — это те же реплики `NetState`, что получает пилот. Экономим и код,
и трафик (один поток вместо двух). Единственное, чего `NetState` не несёт —
`tickApplied`/`maskApplied` (какой именно ввод сервер применил к этому снимку).
Для реконсиляции по `prototype-plan` (откат + переигровка вводов с `tick > tickApplied`)
это нужно. Решение: заводим в `NetState` ещё два реплицируемых поля —
`AppliedTick` и `AppliedMask` (см. шаг 2.3). Это дешевле отдельного RPC и ложится
в уже проверенный механизм репликации.

> Проверка обязательна: после смены авторитета на `1` пилот обязан начать получать
> реплики `NetState` (их раньше он не получал именно как авторитет). Если пилот
> реплик не видит — реконсиляция невозможна, и тогда возвращаемся к варианту
> отдельного `RpcShipSnapshot` (запасной путь, в плане помечен на шаге 2.4).

### 1.6 Предсказание и reconciliation на пилоте

- Кольцевой буфер неподтверждённых вводов: `InputFrame[256]` по индексу `tick & 255`.
- Каждый физшаг пилот: (а) отправляет кадр ввода, (б) интегрирует своё
  **предсказанное** `FlightState` тем же `FlightModel.Integrate`, (в) рисует
  `ShipHull` по предсказанию. Тело при этом заморожено (`Freeze = Static`) — пилот не
  имеет права двигать истину, и это ровно то, что запрещает `prototype-plan` §0.
- При приёме реплики `NetState` (эталон с `AppliedTick`/`AppliedMask`): если
  `|predPos - netPos| > 0.05` м (`prototype-plan` строка 57) — откат предсказанного
  `FlightState` к эталону и переигровка всех вводов с `tick > AppliedTick` из буфера;
  иначе — только подтянуть скорости (soft sync), без телепорта, чтобы не было
  микро-дёрганья.
- `Prediction Error` в панель: расстояние между предсказанием и последней принятой
  репликой `NetState`, метры.

### 1.7 Удалённые корабли

Уже готово: кольцевой буфер снимков + `InterpDelay = 0.1` (`Ship.cs:66`, `Ship._Process`).
Меняется только источник: снимки берутся из `NetState`, которую пишет `Synchronizer`
(он снова авторитетно-серверный). Кнопка `Toggle Interpolation` — в дебаг-панель.

## 3. Чего в этой стадии НЕ делаем

- Стрельба, хитскан, мишени — стадия 3.
- Урон от столкновений и пружина стыковки — стадии 4/5 (ради них и делается В14).
- Автопилот и «кабина без пилота летает сама» — стадия 6; сейчас корабль без пилота
  просто летит по инерции (сервер интегрирует пустой ввод).
- Оптимизация трафика (квантование, delta-encoding) — только если 2.6 (г) не проходит.
- Headless-экспорт сервера — `prototype-plan` это допускает, но проверяться будет на
  стадии 6.

## 4. Риски и как они проверяются

1. **Недетерминизм предсказания vs сервера** → рывок на каждом снапшоте.
   Проверка: автотест п.1 (побитовое равенство) + `Prediction Error` при нулевом
   лаге ≈ 0. Если не ноль — виноват не `FlightModel`, а место, где состояние
   читается/пишется в узел (например, `GlobalRotation` вместо базиса).
2. **`CustomIntegrator` и столкновения.** Кастомный интегратор обходит штатное
   интегрирование, но контакты остаются: при касании корпуса серверное тело может
   «застревать», потому что мы пишем `GlobalPosition` напрямую. Проверка: прогон
   `run-net-demo.sh`, врезание в `TestStand`; при проблеме — `MoveAndCollide`
   вместо прямой записи (решение принимается по факту прогона, не заранее).
3. **`unreliable`-потеря снапшота** → пилот не получает эталон и «уходит» в
   предсказание. Проверка: счётчик принятых снапшотов в панели; при 0 при живом
   соединении — канал/гейт настроены неверно.
4. **Гонка `SetPilot` и спавна узла** (rework §2.10 п.16) — уже лечится очередью
   `TryGetPendingAuthority`; переименование не меняет механику, но очередь обязана
   остаться (`Ship._Ready`, `Ship.cs:126`).
5. **Двойное интегрирование у пилота.** Пилот обязан иметь `Freeze = true` (он не
   авторитет тела) и интегрировать только своё `FlightState`. Если забыть `Freeze` —
   пилот параллельно двигает тело, и картинка двоится. Проверка: assert
   `ship.Freeze == true` на клиенте-пилоте в `NetTest`.
