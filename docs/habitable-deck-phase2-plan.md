## Чего не хватает (пробелы фазы 1 → работа фазы 2)

1. **Сеть шлюза.** `Airlock.cs` локальный: нет RPC/реплики — в двухпиринговом
   демо двери разъедутся, цикл шлюзования у пиров не повторится.
2. **Undock с живым игроком на чужом креплении.** `UndockNow` не отстёгивает
   Reparent-игрока с чужой Hatch-точки → «зависшее дерево» на улетевшем hull.
3. **Обитаемость из каталога.** `HabitableVolume` нет в `ShipTypeSpec`:
   у Hauler/ContainerFreighter кабина курьера; двухпалубных нет.
4. **HUD-контекст «где я»:** `CABIN | HULL | STATION` + «внутри захваченного».
5. **Курьер из Blender:** `sc_courier.blend` untracked, меш-визуал уже в
   `Ship.tscn` (`ShipHull/CourierModel`), но приёмка геометрии (manifold,
   нормали, фаски 50°/80°/30° под `CanStepOn`) не пройдена; второй шлюз
   (`HatchR`) не поставлен.
6. **Прессовка тестов:** `run-all.sh` не прогоняет HabDeckTest/AirlockTest/CapRideTest.

## Этапы фазы 2 (каждый — runnable инкремент)

### F2.1 — Сетевой цикл шлюза (главный пробел)

- `Airlock.cs`: состояние дверей — источник истины **сервер** (peer 1), как
  пилот/док-фазы. Чистая функция переходов — `core/AirlockCycle.cs`
  (enum переходов + `Try(DoorState, HatchAction) → new state | отказ`),
  автест без движка; инвариант: обе двери открыты недостижим.
- RPC-паттерн проекта (`RpcRequestDocking` как образец): клиент
  `RpcId(1, nameof(RpcHatchRequest), airlockNetId, action)`; сервер валидирует
  (шлюз в реестре, игрок рядом/внутри по серверной позе) → меняет состояние →
  `Rpc`-рассылка `ApplyDoorState(airlockNetId, extOpen, intOpen)` всем пирам
  (надёжный, канал 1 — события редкие, трафик на покое не растёт).
- `NetId` шлюза: `Airlock._Ready` регистрируется в `NetworkManager` при
  наличии (по образцу `RegisterAttachPoint`), id — из инстанс-пути (стабилен
  между пирами, как ShipNetId из спавна).
- `HatchTryInteract` остаётся локальным хинтом + отправкой запроса на сервер;
  фактическое изменение дверей — только через `ApplyDoorState`. В оффлайне
  (`MultiplayerServer == false` — стенды) путь не меняется: стендовые тесты
  AirlockTest должны остаться зелёными без правок.
- Проверка: новый автест `AirlockCycleTest` (чистая функция);
  `LATENCY=100 ./run-net-demo.sh 2` — второй пир видит те же двери;
  регрессия `AirlockTest`, `HabDeckTest`.

### F2.2 — Undock-guard для чужих Hatch-креплений

- В `Ship.Docking.UndockNow` (сервер): если у игрока `AttachedTo` указывает на
  `AttachPoint` отстыковываемого корабля — серверный `Detach` + `ApplyDetach`
  у всех пиров (тот же путь, что `RequestAttach/ApplyAttach`). Игрок после —
  джетпак (после detach вне своей палубы) или ботинки (на своей).
- Проверка: регресс-тест AirlockTest/HabDeckTest: игрок на чужом шлюзе →
  undock → ни у кого нет игрока-потомка улетевшего hull; дерево совпало.

### F2.3 — HabitableVolume в каталоге кораблей

- `ShipTypeSpec`: `HabitableVolume` (габарит палубы относительно hull) +

  рассинхрона), `Ship.tscn`-стены курьера переезжают в генератор либо
  остаются как частный случай (решение на шаге — по diff).
- Тесты: п.7.4–7.5 HabDeckTest (двухпалубный переход через проём, отказ на
  скосе 61°).

### F2.4 — HUD-контекст

# Описание механик для тестировщиков (фазы 1 + 2)

## Что должно работать уже сейчас (фаза 1)

**Кабина курьера.** Спавн в кресле, `F` — отстегнуться: игрок **стоит на
палубе в магнитных ботинках** (не в джетпаке). Индикатор «МАГНИТНЫЕ БОТИНКИ»
горит. `WASD` — ходьба по палубе; в стены кабины упирается, вылететь сквозь
обшивку наружу нельзя — выход только через шлюз (правый борт, `+Z` шлюза).
Корабль при этом летает (`W/S` пилоту не нужны — проверять с ботинками):
игрок на палубе **не соскальзывает** при разгоне, крене и рыскании; камера
держит «ноги к палубе».

**Шлюзование наружу→внутрь (клавиша F у шлюза, последовательно):**
1. Снаружи в космосе у закрытого шлюза: F → «открыть наружную дверь»
   (подсказка наводится при наведении курсора в радиусе ~2.2 м). Полотно
   уезжает в сторону, коллизия пропадает.
2. Влететь джетпаком внутрь коробки (1×1×2 м). Внутри — всё ещё джетпак.
3. F → цикл шлюзования: наружная дверь закрывается, **игрок разворачивается
   ногами к полу шлюза** (магнитные ботинки; если влетел вверх ногами — всё
   равно встанет), внутренняя дверь открывается.
4. Шагнуть внутрь — переприлипание на палубу курьера; carry работает.
Обратный путь — F в ботинках внутри шлюза: закрыть внутреннюю → снять ботинки
→ открыть наружную → вылет в космос.
Инвариант: **обе двери одновременно не открыты никогда**. F «не съедается»,
если делать нечего (работает обычная подсказка панели).

**Захват с игроком (Cap-тесты).** Игрок в скафандре **никогда** не захватывается
пузырём крупного корабля (летает свободно). Малый корабль с пилотом в кресле
или игроком на палубе крупным захватывается и тащит за собой всадника без
выбросов.

**Где править:** константы — `SuitModel` (порог `CanStepOn` 60°, ботинки),
`Player.Hatch.HatchRangeM = 2.2 м` (радиус F у шлюза), `Airlock` (габарит
коробки x/z ±0.6, y 0..2.1 — у гейта «внутри» запас ±0.2).

## Что появится в фазе 2 (что проверять после каждого этапа)

- **F2.1:** в двухпиринговой игре шлюз работает у обоих: клиент нажимает F —
  двери у второго пира открываются так же; второй пир **не** может открыть
  дверь «со стороны сервера» без игрока рядом; дерганье обеих дверей
  одновременно невозможно у обоих; оффлайновые тесты не изменились.
  Трафик на покое (2 пир, никто не трогает шлюз) — не растёт.
- **F2.2:** игрок стоит на шлюзе **пристыкованного** корабля; оставив его там,
  отстыковка (радио) → игрок отстёгнут сервером, не улетел вместе с чужим
  hull-деревом, оказался в джетпаке рядом с чужим шлюзом; ни один пир не
  наблюдает «висящего» игрока-потомка.
- **F2.3:** у Hauler/ContainerFreighter своя кабина (габарит из каталога),
  у двухпалубного корабля — трап вверх: `Space` через проём прилипает к
  верхней палубе; по скосу 61° ботинки отказывают («круто» + подсказка).
- **F2.4:** HUD-строка контекста: в кабине — `CABIN`, снаружи на обшивке в
  ботинках — `HULL`, на станции — `STATION`; в кабине корабля, засосанного
  крейсером — «внутри захваченного корабля».
- **F2.5:** на внешнем корпусе курьера видны три фаски: по 50° и 30° ботинки
  ходят, 80° — отказ с подсказкой. Меш без дыр/самопересечений (визуально).
  Второй (левый) шлюз работает идентично правому, включая F-подсказку.
