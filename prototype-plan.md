План разработки прототипа (Godot 4 + .NET, серверная симуляция)
0. Сетевая архитектура (решения до написания кода)
Модель: выделенный сервер (dedicated server) как авторитетный симулятор. Клиенты — «тонкие терминалы»: отправляют ввод, получают состояние. Сервер никогда не доверяет клиентским позициям, урону или результатам выстрелов.

Транспорт: ENetMultiplayerPeer (UDP, надёжные и ненадёжные каналы) — стандарт для real-time в Godot 4. WebSocket — только если позже понадобится браузер.

Авторитет (authority): каждый узел, который симулируется на сервере, имеет SetMultiplayerAuthority(1) (ID сервера). Клиентский ввод идёт через rpc_id(1, ...) с пометкой any_peer; серверные апдейты — rpc с пометкой authority. IsMultiplayerAuthority() используется для гейтинга ввода и физики на клиенте.

Синхронизация состояния: MultiplayerSynchronizer на каждом сетевом узле. Синхронизируются только минимально необходимые свойства (позиция, поворот, линейная/угловая скорость, HP, состояние стыковки). MultiplayerSpawner — для создания мишеней, кораблей и персонажей на всех пирах.

Сглаживание: MultiplayerSynchronizer шлёт обновления с интервалом (например, 30 Гц), рендер идёт на 60+ Гц. Без интерполяции удалённые объекты будут «дёргаться». Для удалённых (не-авторитетных) сущностей используется snapshot interpolation с буфером ~100 мс.

Локальное ощущение: для собственного корабля/персонажа — client-side prediction + server reconciliation: клиент применяет ввод сразу, запоминает его в ring buffer, а при получении серверной коррекции откатывается и переигрывает неподтверждённые вводы. Рекониляция только если расхождение выше порога (например, 0.05 м), иначе микро-дёрганье.

Урон и столкновения: считает только сервер. Клиент не присылает «я попал» или «я врезался» — он присылает ввод (выстрел, направление), сервер симулирует, применяет урон и рассылает результат.

Режим для прототипа: на первом этапе допустим host-client (один из клиентов запускает сервер и играет сам), но код пишется так, чтобы позже можно было вынести сервер в headless-бинарь без переписывания логики. Headless-экспорт в Godot 4 для C# требует Mono-enabled server binary и флага --headless.

1. Этапы (в порядке приоритета, с учётом сети)
Этап 1. Фундамент: дебаг-оболочка + сетевая оболочка (1 неделя)
Цель: к концу недели есть запускаемый сервер и подключаемый клиент, а также тестовый стенд для отладки всего остального. Сеть и дебаг идут первыми — без них невозможно проверять сетевые механики.

Задачи:

Godot-проект, слои коллизий, отключение глобальной гравитации.

Сетевая оболочка:

NetworkManager (autoload): ENetMultiplayerPeer, CreateServer(port, max), CreateClient(ip, port). Сигналы PeerConnected, PeerDisconnected, ConnectedToServer, ConnectionFailed.

Проверка: сервер запускается, клиент подключается, в консоли видны ID пиров.

Дебаг-оболочка (DebugLayer, CanvasLayer):

Button «Debug Mode» (зелёный текст) в левом верхнем углу, F3 — toggle видимости.

Клик — PanelContainer с VBoxContainer.

Метод RegisterDebugButton(string label, Action callback) — кнопки добавляются одной строкой по мере роста фич.

Сетевые дебаг-кнопки сразу: Host, Join, Disconnect, Label с Peer ID и Server/Client статусом.

Критерий готовности: два экземпляра игры соединяются, дебаг-панель показывает роль (сервер/клиент) и список пиров.

Этап 2. Пилотирование корабля 6DoF с серверной симуляцией и клиентским предсказанием (1.5–2 недели)
Цель: корабль летает, но позицию определяет сервер, а клиент предсказывает для отзывчивости.

Задачи:

ShipController на RigidBody3D: gravity_scale = 0, linear_damp ≈ 0, angular_damp ≈ 1.5.

6DoF-управление (A/D, Ctrl/Space, W/S, Z/X, Q/E, мышь) — как в локальном плане, но:

Клиент не применяет силы напрямую к RigidBody3D. Вместо этого он собирает InputFrame (битовая маска нажатий + ось мыши) и отправляет на сервер rpc_id(1, "SubmitInput", inputFrame, tick) с unreliable.

Для собственного корабля клиент предсказывает движение: локально применяет тот же ShipController-код к «призрачному» состоянию и рендерит его. Это позволяет управлению ощущаться мгновенно.

Сервер получает ввод, применяет его к RigidBody3D корабля (авторитетная симуляция), и рассылает подтверждённое состояние (позиция, поворот, скорость) через MultiplayerSynchronizer или явный rpc.

Клиент при получении коррекции делает reconciliation: откат к серверной позиции + переигровка неподтверждённых вводов из буфера.

Синхронизация удалённых кораблей: snapshot interpolation с буфером 100 мс, чтобы чужие корабли не дёргались.

В дебаг-панель: Ping, Server Tick, Prediction Error (расхождение между предсказанной и серверной позицией), Toggle Interpolation.

Критерий готовности: при пинге 100 мс управление ощущается отзывчивым; при искусственной задержке корабль не «резинит»; чужой корабль движется плавно.

Это самый сложный этап по сети. Если он «поплывёт», дальше всё будет нестабильно, поэтому на него заложено 2 недели.

Этап 3. Стрельба хитсканом + мишени с серверной валидацией (1 неделя)
Цель: лазер визуально стреляет мгновенно у клиента, но попадание и урон подтверждает сервер.

Задачи:

Клиент: при ЛКМ отправляет на сервер rpc_id(1, "RequestFire", aimPoint, tick). Локально сразу рисует луч (белая полоса на 0.2 сек) — это «предсказание» визуала, не более.

Сервер: получает aimPoint, делает собственный IntersectRay из Muzzle корабля в эту точку, проверяет попадание в мишень и применяет урон. Рассылает результат (rpc("OnHitConfirmed", targetId, damage, hitPoint)).

Мишени: MultiplayerSpawner спавнит мишени на всех пирах по команде сервера. TargetHealth синхронизируется через MultiplayerSynchronizer (HP как int, хелсбар обновляется на основе синхронизированного HP).

В дебаг-панель: Spawn Target (только для сервера/host), Clear Targets, Server-side hit logs.

Критерий готовности: при выстреле клиент видит луч мгновенно; если сервер подтвердил попадание — HP мишени падает у всех; если клиент «схитрил» и прислал ложный aimPoint — сервер всё равно считает по своей симуляции.

Этап 4. Станция + урон от столкновений (серверный расчёт) (1 неделя)
Цель: станция как статичный авторитетный объект; урон от столкновений считает только сервер.

Задачи:

Станция: StaticBody3D + CylinderShape3D, DockingPoint, огни (выключены). Станция существует на сервере и реплицируется клиентам (как StaticBody3D она не симулируется клиентом).

Урон от столкновений (ShipHealth):

Сервер в _IntegrateForces() (или через BodyEntered + относительная скорость × масса) вычисляет импульс и применяет урон только к авторитетному кораблю.

Клиент получает обновлённый HP через MultiplayerSynchronizer и обновляет UI/хелсбар. Клиент не считает урон сам.

В дебаг-панель: Toggle God Mode (только сервер), Show HP в debug-info.

Критерий готовности: таран на высокой скорости снимает HP у всех клиентов одинаково; медленное касание — нет; клиент не может «отменить» урон.

Этап 5. Стыковка с серверной авторитетностью (1.5 недели)
Цель: полный цикл «радиосвязь → огни → захват → посадка», где сервер решает, можно ли стыковаться, а клиенты видят результат.

Задачи:

Радиосвязь: клиент в зоне DockingZone жмёт F → rpc_id(1, "RequestDocking"). Сервер проверяет: корабль в зоне? скорость ниже порога? Если да — включает огни (синхронизированное свойство DockingApproved = true) и переходит в состояние захвата.

Мягкая стыковка:

Сервер применяет пружину/Joint3D к авторитетному кораблю.

Клиенты видят движение корабля через синхронизацию (интерполированно), но не симулируют пружину локально.

После фиксации сервер ставит Freeze = true и синхронизирует состояние Docked.

В дебаг-панель: Teleport to Docking Zone (только сервер/host), Docking State в debug-info.

Критерий готовности: стыковка запускается клиентом, но выполняется сервером; все клиенты видят одинаковое состояние; при отключении клиента посреди стыковки сервер корректно завершает или отменяет процесс.

Этап 6. Персонаж + магнитные ботинки с серверной симуляцией (2–2.5 недели)
Цель: персонаж ходит по станции и улетает в невесомость, но его позицию и столкновения считает сервер.

Задачи:

Спавн персонажа: сервер спавнит CharacterBody3D для каждого подключившегося пира через MultiplayerSpawner. Авторитет — сервер.

Ввод: клиент отправляет InputFrame (направление, toggle ботинок, jump) на сервер. Сервер двигает CharacterBody3D и применяет магнитные ботинки (raycast, выравнивание по нормали, гравитация к поверхности).

Предсказание: для собственного персонажа клиент предсказывает движение локально (те же формулы), сервер корректирует при расхождении > порога.

Удалённые персонажи: snapshot interpolation.

Toggle ботинок: клиент отправляет команду, сервер переключает состояние и синхронизирует BootsOn (bool).

В дебаг-панель: Teleport to Platform (сервер), Boots State в debug-info, Prediction Error для персонажа.

Критерий готовности: два клиента видят, как персонажи друг друга ходят по станции; при отключении ботинок и прыжке персонаж улетает по инерции, и это видят все; сервер не даёт клиенту «пролететь сквозь станцию».

Этап 7. Headless-сервер, интеграция и полировка (1.5 недели)
Задачи:

Headless-экспорт: отдельный export preset Linux Server с флагом Export As Dedicated Server, --headless при запуске, проверка через OS.HasFeature("dedicated_server") или DisplayServer.GetName() == "headless". C# требует Mono-enabled server binary.

Сквозной сценарий (2 клиента + сервер): «оба подключились → один подлетел → запросил стыковку → сел → вышел → прошёлся → отключил ботинки → улетел → второй выстрелил в мишень → оба видят результат».

Полировка: пороги рекониляции, интерполяция, демпфирование, частота синхронизации (30 Гц по умолчанию, при необходимости — адаптивно).

Критерий готовности: выделенный сервер запускается без GPU/дисплея; два клиента проходят полный цикл без рассинхрона и «резина».

3. Риски, специфичные для сетевой версии
Риск	Почему опасен	Смягчение
«Резина» при рекониляции	Клиент и сервер расходятся, коррекция видна как рывок	Порог рекониляции (0.05 м), переигровка только неподтверждённых вводов, не снапить каждый кадр
Jitter удалённых объектов	Синхронизация 30 Гц при рендере 60+ Гц	Snapshot interpolation с буфером 100 мс; не обновлять GlobalPosition напрямую, а лерпить
Читерство клиента	Клиент может прислать ложную позицию/урон	Всё, что влияет на мир, валидируется сервером; клиент присылает только ввод
Рассинхрон спавна	MultiplayerSpawner не успевает создать объект у позднего клиента	Использовать SpawnFunction с явным именем и проверять наличие узла перед RPC; при подключении — полный снапшот мира
Headless + C#	Не все сборки Godot поддерживают Mono в server-режиме	Использовать официальный Mono-enabled server binary; тестировать --headless с самого начала
Физика на клиенте «врёт»	Клиент симулирует RigidBody3D, но сервер решает иначе	Для собственного корабля — предсказание + рекониляция; для чужих — не симулировать физику, только интерполировать синхронизированное состояние
4. Минимальный сетевой стек для прототипа
ENetMultiplayerPeer — транспорт.

NetworkManager (autoload) — host/join/disconnect, сигналы.

MultiplayerSpawner — спавн кораблей, персонажей, мишеней.

MultiplayerSynchronizer — HP, состояние стыковки, булевы флаги (лёгкие свойства).

Явные RPC — для ввода, выстрелов, запросов стыковки (потому что это команды, а не «состояние»).

Ring buffer + reconciliation — для собственного корабля и персонажа.

Snapshot interpolation — для всех удалённых сущностей.
