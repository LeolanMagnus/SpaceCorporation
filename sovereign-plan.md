# План: владение имуществом и доверенности (sovereignty)

> Статус: **проект плана, кода ещё нет.** Файл — черновик архитектуры; решения,
> помеченные **[ВЫБОР]**, требуют подтверждения перед реализацией.
>
> Цель механики: у игрока и его имущества (корабль, станция) появляется уникальный
> владелец; любая операция с чужим имуществом (сесть за штурвал, открыть терминал
> станции) проверяет право доступа. Плюс — доверенности: игроки договариваются и
> выдают друг другу право управлять (всем имуществом / кораблями / одним кораблём /
> станциями / одной станцией).

---

## 0. Что уже есть в архитектуре (на что опираемся)

Прежде чем добавлять новое — фиксируем готовые кирпичи, чтобы не изобретать дубли.

1. **Идентичность игрока — `playerKey`, а не `peerId`.**
   `playerKey` — GUID-строка из `user://identity.cfg` (`NetworkManager.PlayerKey`),
   стабилен между переподключениями. `peerId` (`unique_id` ENet) эфемерен: выдаётся
   заново при каждом коннекте. Таблицы `NetworkManager`: `_peerPlayers`
   (peerId→Player), `_peerKeys` (peerId→playerKey), `FindPeerHoldingKey(playerKey)`.
   **Вывод: владельцем и в списках доверенности храним `playerKey`, а не `peerId`.**
   Иначе доверенность «протухнет» при переподключении.

2. **Сетевой адрес объекта — `NextNetId()`.** Один монотонный счётчик на все
   спавнящиеся объекты мира (`ShipNetId`, будущий `StationNetId`). Лежит в
   `NetState.ShipNetId` (`[Export]`, реплицируется). `AttachPoint` знает
   `OwnerNetId` (адрес владельца точки). **Вывод: имущество идентифицируется в сети
   по `NetId` объекта, а владелец — по `playerKey`.**

3. **Авторитет узла (`SetMultiplayerAuthority`) уже решает «кто может двигать».**
   `Ship.RequestImpulse` гейтится `IsRequestFromOwner` (сверка `GetRemoteSenderId()`
   с авторитетом узла). Посадка за кресло (`Player.AttachServerSide`) вызывает
   `AssignShipAuthority(shipNetId, pilotPeer)` — и **сейчас это происходит без
   какой-либо проверки владельца**: любой игрок может сесть на любой корабль и
   получить авторитет. **Это и есть главная дыра, которую закрываем.**

4. **Паттерн «серверный RPC, инициированный клиентом»** уже отработан:
   `RequestAttach`/`RequestDetach`/`AssignShipAuthority` —
   `[Rpc(RpcMode.AnyPeer, CallLocal=false, TransferMode=Reliable)]` + гейт
   `IsRequestFromOwner`. Выдачи доверенностей повторяют этот же путь.

5. **Репликация состояния — через `[Export]`-свойства `NetState`** +
   `MultiplayerSynchronizer`. C#-поле без `[Export]` не реплицируется (§3.11 п.2).
   **Вывод: поле владельца/список прав, нужный клиентам для UI, кладём в `[Export]`.**

6. **Дебаг-панель**: `DebugInfoBus.RegisterDebugButton(label, cb) → DebugButtonHandle`,
   `RegisterInfoSource`/`RemoveInfoSource`. Через неё тестируем выдачу/отзыв прав.

## 1. Модель данных: кто чем владеет и кому доверяет

### 1.1. Ключ доступа — `playerKey` (строка)

Все списки прав оперируют `playerKey`. `peerId` появляется только в момент
проверки «жив ли сейчас доверенный игрок» (для UI/подсказки), но не как ключ.

> **[ВЫБОР A1]** Хранить `playerKey` как `string` (GUID) или как стабильный
> `int`-таблетку (сервер выдаёт каждому ключу числовой `PlayerId`)?
> Рекомендую **`string` GUID** как источник истины (уже есть, переживает рестарт
> сервера), а числовой `PlayerId` — только опциональная внутренняя оптимизация.
> Для прототипа — `string`.

### 1.2. Право (permission) — enum

```
enum AccessRight {
    ManageAll,        // управлять ВСЕМ имуществом владельца (и корабли, и станции)
    ManageShips,      // управлять ВСЕМИ кораблями владельца
    ManageStations,   // управлять ВСЕМИ станциями владельца
    ManageShip,       // управлять ОДНИМ кораблём (привязано к конкретному объекту)
    ManageStation,    // управлять ОДНОЙ станцией (привязано к конкретному объекту)
}
```

Иерархия «шире ⊃ уже» при проверке: `ManageAll` ⊃ (`ManageShips`|`ManageStations`)
⊃ (`ManageShip`|`ManageStation`). То есть если у игрока есть `ManageAll` от
владельца X — он может всё имущество X; `ManageShips` — любой корабль X;
`ManageShip` — только тот конкретный корабль, на который выдана доверенность.

### 1.3. Где живёт запись о праве

Пользователь предложил: «у объектов имущества поле со списком всех, кто имеет
доступ». Это рабочий вариант для **конкретного** имущества (`ManageShip`/
`ManageStation`). Но `ManageAll`/`ManageShips`/`ManageStations` — права **на классы
имущества одного владельца**, их неудобно дублировать в каждом объекте (при выдаче
`ManageAll` пришлось бы переписать списки во всех кораблях и станциях, включая
будущие).

Поэтому предлагаю **гибрид** (и это ключевое архитектурное предложение плана):

- **На объекте имущества** (`Ship`, будущая `Station`) — поле владельца
  `OwnerKey` (один `playerKey`) и список **точечных** доверенностей на этот объект:
  `Dictionary<playerKey, AccessRight>` (только `ManageShip`/`ManageStation`).
- **На сервере (в `NetworkManager`)** — таблица **классовых** доверенностей:
  `Dictionary<grantorKey, Dictionary<granteeKey, AccessRight>>` для
  `ManageAll`/`ManageShips`/`ManageStations`. Это «между игроками», а не «между
  игроком и объектом», поэтому логично держать в менеджере, а не в каждом объекте.

Проверка доступа (сервер, авторитет) объединяет оба источника:

```
bool CanManage(playerKey grantee, Property prop):
    if prop.OwnerKey == grantee: return true                 // владелец всегда может
    if prop.ObjectGrants.ContainsKey(grantee): return true    // точечная (ManageShip/Station)
    // классовые доверенности от владельца объекта:
    var cls = GrantsFrom(prop.OwnerKey).TryGet(grantee)
    if cls == null: return false
    if prop is Ship   && cls in {ManageAll, ManageShips}: return true
    if prop is Station&& cls in {ManageAll, ManageStations}: return true
    return false
```

> **[ВЫБОР A2]** Гибрид (объект хранит владельца + точечные права, менеджер —
> классовые) vs «всё в объекте» (как предложил пользователь) vs «всё в менеджере».
> Рекомендую гибрид: точечные права локальны объекту (переживают пересоздание
> игрока, реплицируются с объектом), классовые — глобальны и не размазываются по
> всем объектам. Пользовательский вариант «список в объекте» сохраняется как
> частный случай точечных прав.

### 1.4. Владение: как объект получает владельца

- **Корабль/станция спавнятся сервером** (уже так, §4 В4). В момент спавна сервер
  назначает `OwnerKey`:
  - корабль, заспавненный «из ничего» (world spawn) — `OwnerKey = ""` (сирота,
     бесхозный) или `OwnerKey = <ключ инициатора события>`, если событие имел автора;
  - корабль, собранный/выданный игроком — `OwnerKey = playerKey` игрока.
- **Привязка владельца — серверная** (авторитет решает). Клиент не может сам
  объявить себя владельцем: только сервер пишет `OwnerKey` и рассылает реплику.
- **`OwnerKey` реплицируется** как `[Export]` в `NetState` (или в новый дочерний
  узел `OwnershipState`, см. §3), чтобы клиенты видели «чей корабль» в UI.

> **[ВЫБОР A3]** Бесхозное имущество (`OwnerKey == ""`): можно ли сесть?
> Рекомендую для прототипа: **бесхозное — свободно** (первый севший становится
> владельцем по правилу «захват», см. §2.4). Это даёт тестовый полигон без
> предзаданных владельцев. Альтернатива — бесхозное запрещено, всё раздаёт сервер.

## 2. Механика владения (ownership)

### 2.1. Инварианты

1. У любого имущества ровно один владелец (`OwnerKey`), либо пусто (бесхозно).
2. Владелец может всё со своим имуществом без доверенностей.
3. Не-владелец получает доступ **только** через доверенность (§4).
4. Авторитет узла (`SetMultiplayerAuthority`) выдаётся **только** тому, кому
   разрешено управлять (см. §5) — это второй, «физический» контур защиты.

### 2.2. Точка проверки (главный гейт)

Единственное место, где сейчас «даётся власть» над объектом —
`Player.AttachServerSide(ownerNetId, pointNetId)` (Player.cs:365–397): при посадке
на `Kind.Seat` он безусловно зовёт `AssignShipAuthority`. **Добавляем гейт прямо
там:** перед `AssignShipAuthority` сервер спрашивает
`Ownership.CanManage(playerKey, ship)`. Если `false` — посадка за штурвал
отклоняется (игрока можно посадить на `Kind.Floor`/пассажирское место, но не на
кресло-пилота). Аналогичный гейт появится у терминала станции (§6).

> Ключевое: проверка на **сервере/авторитете**, не на клиенте. Клиентский UI лишь
> подсказывает (кнопка «Сесть» неактивна), но настоящий отказ — серверный, как и
> `IsRequestFromOwner` в существующих RPC.

### 2.3. Что именно «использование имущества» для прототипа

- **Корабль:** сесть за штурвал (`Kind.Seat`) → получить авторитет → `RequestImpulse`.
  Всё это уже идёт через авторитет, поэтому гейт на посадке закрывает и импульс.
- **Станция:** открыть терминал управления (будущая `Station`, §6). Для прототипа —
  действие «взаимодействие с терминалом» (открыть панель/команду), гейтится так же.

### 2.4. Захват бесхозного (предложение плана)

Чтобы механику можно было щупать без редактора владельцев: бесхозный объект
(`OwnerKey == ""`) при первой легальной посадке/взаимодействии **переходит** к
игроку (сервер пишет `OwnerKey = playerKey` и шлёт реплику). Это «право первого
пришедшего». Отключаемо флагом, если захват нежелателен.

## 3. Репликация прав на клиентов

Клиентам права нужны **только для UI** (подсветить «свой/чужой/доверенный»,
деактивировать чужие кнопки). Настоящая проверка — на сервере. Поэтому:

- **Владелец объекта** (`OwnerKey`) — `[Export] string` в `NetState` (или в новом
  дочернем узле `OwnershipState : Node` рядом с `NetState`, с
  `[Export] string OwnerKey` и `[Export] string[] GranteeKeys`). Узел-хранилище
  вписывается в уже отработанный паттерн `NetState` + `MultiplayerSynchronizer`
  (`RootPath = ".."`). **Рекомендую отдельный `OwnershipState`**, чтобы не раздувать
  `NetState` (он про физику) и чтобы репликация прав не мешала физическому потоку.
- **Точечные доверенности объекта** (`ManageShip`/`ManageStation`) — `[Export]
  string[]` (список ключей) в том же `OwnershipState`. Для прототипа массива ключей
  достаточно (право на объект однозначное: если ключ в списке — может управлять
  этим объектом).
- **Классовые доверенности** (`ManageAll`/`ManageShips`/`ManageStations`) живут на
  сервере и **не реплицируются целиком**; вместо этого сервер при посадке/терминале
  сам решает «можно/нельзя» и рассылает итог (например, `AssignShipAuthority` уже
  доходит до клиента как факт «тебе дали авторитет»). Для UI-подсказки «у меня есть
  право на этот корабль» сервер может точечно сообщить одному пиру (см. §4.4).

> **[ВЫБОР A4]** Отдельный узел `OwnershipState` vs расширить `NetState`.
> Рекомендую отдельный узел: чище разделение ответственности, независимый
> `MultiplayerSynchronizer` с меньшей частотой (права меняются редко).

## 4. Механика доверенностей (alliance / delegation)

### 4.1. Союз (alliance) — контейнер доверенностей

«Заключить союз» = взаимный/односторонний обмен правами. Для прототипа союз — это
не отдельная сущность с голосованием, а **набор выданных доверенностей** между
двумя `playerKey`. Союз можно моделировать как быстрый пресет: «союз по умолчанию»
= взаимная выдача `ManageShips` (+`ManageStations`, когда станции появятся).

> **[ВЫБОР A5]** Союз как отдельный объект (id союза, список членов, общий
> пул прав) vs просто направленные доверенности «игрок→игрок». Для прототипа
> рекомендую **направленные доверенности** (проще, покрывает «доверять права друг
> другу»), а союз — тонкий пресет поверх. Полноценный альянс с id — отложить.

### 4.2. Выдача/отзыв права — серверные RPC

Повторяем паттерн `AssignShipAuthority`:

```
[Rpc(AnyPeer, CallLocal=false, Reliable)]
void RequestGrant(string granteeKey, AccessRight right, int targetNetId)
    // гейт: автор должен быть владельцем цели (для ManageShip/Station)
    //       или «я могу управлять всем/классом» (для ManageAll/Ships/Stations)
    // сервер вносит запись в объект (точечная) или в таблицу менеджера (классовая)
    // + реплика

[Rpc(AnyPeer, CallLocal=false, Reliable)]
void RequestRevoke(string granteeKey, AccessRight right, int targetNetId)
```

`targetNetId` = адрес конкретного корабля/станции для `ManageShip`/`ManageStation`;
для классовых прав = 0 (не используется).

### 4.3. Таблица классовых доверенностей (сервер)

```
// NetworkManager
Dictionary<string grantorKey, Dictionary<string granteeKey, AccessRight>> _classGrants;
```

Хранится на сервере (авторитет). Клиенты её не видят целиком — им хватает
итоговых решений (§3). При отзыве союза удаляем записи grantor↔grantee.

### 4.4. Проверка доступа (сервер) — единая функция

```
bool CanManage(string granteeKey, Property prop):
    if (prop.OwnerKey == granteeKey) return true;
    if (prop.ObjectGrants.ContainsKey(granteeKey)) return true;      // точечная
    var cls = _classGrants.TryGet(prop.OwnerKey)?.TryGet(granteeKey);
    if (cls == null) return false;
    return prop.Kind switch {
        Ship     => cls is ManageAll or ManageShips,
        Station  => cls is ManageAll or ManageStations,
        _        => false };
```

Эту функцию зовёт и гейт посадки (§2.2), и терминал станции (§6), и (опционально)
UI-подсказка, которой сервер отвечает отдельным RPC «тебе можно/нельзя на объект N».

### 4.5. Жив ли доверенный игрок

`playerKey` переживает переподключение, но для «сейчас в сети» нужен `peerId`:
`FindPeerHoldingKey(playerKey)`. Если пир отвалился — доверенность **не** сгорает
(ключ-то жива), просто игрок временно не может ей воспользоваться. Это осознанно:
доверенность — долгосрочная запись, а не сессия.

## 5. Связка с авторитетом узла (второй контур защиты)

Существующая модель уже даёт «физический» контур: `Ship.RequestImpulse` принимает
только от текущего `GetMultiplayerAuthority()`. Поэтому:

- Гейт посадки (§2.2) **не даёт** авторитет не-уполномоченному → импульс сам
  отклонится (`IsRequestFromOwner`).
- Дополнительно: при отзыве права **в момент, когда доверенный уже пилотирует**,
  сервер обязан отозвать авторитет (`AssignShipAuthority(netId, 1)` — вернуть
  автопилоту/серверу) и, если нужно, отстегнуть игрока от кресла. Иначе отзыв
  сработает только на следующую посадку.

> **[ВЫБОР A6]** Отзывать ли авторитет немедленно при revoke активного пилота.
> Рекомендую **да** (иначе «выдал-отобрал, а он всё ещё рулит» — дыра). Реализация:
> revoke проверяет `CountShipsPilotedBy(grantee)`/текущий авторитет объекта и
> сбрасывает его.

## 6. Станция и терминал (задел под будущую `Station`)

`Station` ещё не реализована (стадия 6), но `AttachPoint`/физический слой её уже
ожидают. План:

- `Station` наследует тот же контракт, что `Ship`: `NetState`/`OwnershipState`,
  `StationNetId` из того же `NextNetId()`, `AttachPoint`-ы (`Kind.Hatch`/терминал).
- **Терминал управления** — точка взаимодействия (`Kind.Hatch` или новый
  `Kind.Terminal`). «Открыть терминал» = серверный RPC, гейтимый
  `CanManage(playerKey, station)`.
- Права `ManageStations`/`ManageStation` проверяются ровно той же
  `CanManage` (§4.4) — механика общая, меняется только тип цели.

> Реализацию станции можно начать с заглушки: невидимый `Node3D` с `OwnershipState`
> и одной точкой-терминалом, чтобы прогнать права на станциях до полноценной
> геймплейной станции.

## 8. Тесты (расширение NetTest)

NetTest уже эмулирует чужие авторитеты через `SetMultiplayerAuthority`. Добавляем
фазы:

1. **Ownership-deny:** у Ship#1 `OwnerKey = A`; игрок B (чужой авторитет) просит
   `AttachServerSide` на штурвал → отказ, авторитет не выдаётся.
2. **Grant-object:** A выдаёт B `ManageShip` на Ship#1 → B сажается легально.
3. **Revoke:** отзыв → B больше не может; если B активный пилот — авторитет снят.
4. **Class-grant:** A выдаёт B `ManageShips` → B садится на **любой** корабль A;
   `ManageAll` → и на станцию A тоже.
5. **Alliance preset:** взаимный `ManageShips` → оба пилотируют корабли друг друга.
6. **Reconnect-stability:** доверенность по `playerKey` переживает смену `peerId`.

Итоговая метрика как сейчас: `NetTest checks=… failures=0`, `Stage1Test` не
регрессирует.

## 9. Поэтапная реализация (порядок коммитов)

1. **Модель данных:** enum `AccessRight`, `OwnershipState` (`OwnerKey`,
   `GranteeKeys`), публичный `PlayerKey` у `Player`, таблица `_classGrants` в
   `NetworkManager`, функция `CanManage`. (Только данные + чистая функция, без
   гейтов.) Тесты на `CanManage` в вакууме.
2. **Назначение владельца при спавне** + реплика `OwnerKey`. UI-инфо «чей объект».
3. **Гейт посадки за штурвал** (§2.2) + тесты Ownership-deny/grant-object/revoke.
4. **RPC выдачи/отзыва** точечных и классовых прав (§4.2) + тесты class-grant.
5. **Отзыв авторитета активного пилота** (§5, A6) + тест.
6. **Захват бесхозного** (§2.4, A3) — опционально, отдельным флагом.
7. **Заглушка `Station` + терминал** (§6) + тесты на `ManageStations`/`ManageStation`.
8. **Союз-пресет** (§4.1, A5) + дебаг-кнопки (§7).

Каждый шаг — зелёная сборка + зелёные NetTest/Stage1Test перед следующим.

## 10. Мои дополнения и замечания к идее пользователя

1. **Хранить владельца по `playerKey`, а не по `peerId`** — иначе доверенность
   сгорит при переподключении (у нас уже есть `playerKey`, это бесплатно).
2. **Гибрид «объект + менеджер»**, а не «всё в объекте»: классовые права
   (`ManageAll/Ships/Stations`) нельзя эффективно хранить в каждом объекте — их
   надо держать в таблице менеджера. Точечные (`ManageShip/Station`) — в объекте,
   как и предложил пользователь.
3. **Два контура защиты:** логический (`CanManage` на сервере) + физический
   (авторитет узла). Не полагаться только на клиентский UI.
4. **Отзыв должен снимать активный авторитет**, иначе «отобрал право, а он рулит».
5. **Репликация прав — отдельный `OwnershipState`** с редким синхронизатором, чтобы
   не трогать физический `NetState`.
6. **Бесхозное имущество и захват** — чтобы механику можно было тестировать без
   предзаданных владельцев (флаг).
7. **Станцию начать с заглушки** — прогнать права до полноценной станции.
8. **Союз = пресет направленных доверенностей**, а не отдельная сущность (для
   прототипа). Полноценный альянс с id союза — отложить на потом.
9. **Права на класс ⊃ права на объект**: `ManageAll` ⊃ `ManageShips`/`ManageStations`
   ⊃ `ManageShip`/`ManageStation`. Проверка учитывает иерархию.
10. **Открытые вопросы** собраны как **[ВЫБОР A1…A6]** — их стоит закрыть до
    кода (особенно A2 гибрид и A3 бесхозное).
